1. RAG in one minute

Picture a personal digital librarian. You give it a pile of PDFs. It reads every page and files each paragraph on shelves arranged by meaning, not by alphabet. When you ask a question, it walks to the right shelves, pulls out the few most relevant paragraphs, and writes an answer using only those paragraphs, adding footnotes such as "[1] report.pdf, page 7".

🔒

Private and local

Everything runs on your own computer. No document is uploaded to an online AI service and no API key is needed.

📑

Every answer is checkable

The chatbot shows which file and page each fact came from, so you can open the PDF and verify it.

🙅

Honest about gaps

If your documents don't contain the answer, it replies "I couldn't find the answer" instead of inventing one.

2. RAG concepts, from simple to technical

The problem

An AI language model (an LLM) is like a brilliant writer who has read a huge part of the internet but has never seen your PDFs. If you ask about your company's leave policy, it can't know the answer. Worse, it often produces a confident, fluent, completely invented reply. This is called a hallucination.

The idea behind RAG

RAG = Retrieval-Augmented Generation. Think of an open-book exam. A student who memorized nothing can still score well if allowed to look up the right page first. RAG does the same for the AI in two moves:

① Retrieve

Search your documents and find the few paragraphs most related to the question. This is a smart search step. No writing yet.

② Generate

Give the LLM those paragraphs together with the question and say "answer using only this". This is the writing step.

"Augmented" means the AI's knowledge is boosted by extra material you supply at the moment of asking. The AI itself is never retrained. It reads fresh pages every time.

Why not paste the whole PDF into the AI?

An LLM can only read a limited amount of text at once (its "context window"; this project sets it to 8192 tokens, roughly 6,000 words). A 200-page PDF won't fit, and reading more text is slower. RAG sends only the best 5 paragraphs, so it is faster and more focused.

3. Project map: what the folder contains

The project root is chatbot-task/pdf chatbot/. Read the folders from the outside inward: the root launches the app, src/ contains reusable logic, scripts/ contains command-line tools, tests/ proves behavior, and data/ contains the local ChromaDB index created while the app runs.

Root files: app.py, pyproject.toml, requirements.txt

app.py is the Streamlit interface and entry point. pyproject.toml declares the package metadata, Python 3.12 requirement, pytest configuration, source path, and test markers. requirements.txt installs runtime and test libraries such as Streamlit, PyMuPDF, ChromaDB, sentence-transformers, Ollama, and pytest.

src/pdf_chatbot/: the reusable application engine

These modules implement settings, PDF reading, chunking, embeddings, vector storage, reranking, prompts, Ollama communication, shared data records, errors, and the orchestration pipeline. Keeping them outside app.py makes the core testable without opening a browser.

scripts/: manual inspection and setup tools

verify_setup.py checks the local installation and models; chat_cli.py provides a terminal chat; inspect_pdf.py shows extracted pages/chunks; search_pdf.py shows raw vector-search matches. These are debugging windows into the same engine, not separate chatbot implementations.

tests/: executable explanations of behavior

The tests cover the UI helpers, configuration validation, PDF edge cases, chunk boundaries, model records, embeddings/LLM adapters, prompt construction, vector storage, reranking, and end-to-end pipeline behavior. test_llm_live.py is the exception: it needs a running Ollama model.

data/: local runtime state, not source code

data/chroma_db/ is the persistent vector database. It stores chunk text, embeddings, IDs, and metadata so a restart does not require re-indexing every PDF. It is generated state; the Python source explains how to recreate it.

Core concepts you will see in the code

Six ideas make RAG work. Each one below says what it is, why it's needed, how it works and where it lives in this project.

3.1 Large Language Model (LLM): the writer llm.py

An LLM is a program trained on enormous amounts of text. Its core skill is predicting a sensible next word, again and again, which produces whole sentences and answers.

Why:It turns raw paragraphs into a clear, direct answer in plain language.How:It receives instructions plus text, then writes word by word. A low "temperature" (0.1 here) makes it stick to the given facts instead of being creative.Here:qwen3:4b-instruct, a small model (4 billion parameters) that runs on an ordinary computer through the free app Ollama.

3.2 Embeddings: turning meaning into numbers embeddings.py

Computers can't compare "meaning" directly, but they are excellent at comparing numbers. An embedding model reads a piece of text and outputs a long list of numbers (here, 384) that acts like a coordinate on a "map of meaning". Texts that mean similar things get nearby coordinates, even with different words: "annual leave" and "vacation days" sit close together, while "server password" sits far away.

Why:It lets the project search by meaning, which finds answers keyword search would miss.How:The same model embeds every chunk (once, when indexing) and every question (each time you ask), so both live on the same map. Vectors are scaled to length 1 (normalized) so similarity scores are comparable.Here:Model BAAI/bge-small-en-v1.5. It was trained to expect a special instruction in front of questions only, so the code adds "Represent this sentence for searching relevant passages: " to questions but not to chunks.

3.3 Chunking: cutting text into index cards chunker.py

One page often covers several topics, so its single meaning-point is a blurry average. Smaller pieces have a sharp meaning and match questions better. So each page is cut into chunks of up to 1000 characters (about one or two paragraphs).

Chunk 1
Chunk 2
Chunk 3

The orange strips show the overlap: the last ~150 characters of one chunk are repeated at the start of the next.

Why:Sharper matches, shorter prompts. Overlap protects a fact that would otherwise be sliced in half at a boundary.How:Cut at the gentlest boundary available: paragraph first, then sentence, then word, and raw characters only as a last resort. Chunks never cross a page, so each one cites exactly one page.

3.4 Vector store: the searchable filing cabinet vector_store.py

A vector store saves each chunk's text together with its number list and a label (file name, page). Its special skill: given the number list of a question, it quickly returns the stored entries that are closest on the meaning map.

Why:Re-reading every chunk for every question would be far too slow. The database finds nearest neighbours in milliseconds, and it remembers everything after you close the app.How:"Closeness" is measured by cosine similarity: 1.0 means pointing the same way (same meaning), near 0 means unrelated.Here:ChromaDB, saved in data/chroma_db. No separate server is needed.

3.5 Reranker: the careful second opinion reranker.py

The embedding search is fast but shallow, because it compares the question and each chunk separately. A chunk that just shares words like "days" can outrank the one that truly answers. A reranker (a cross-encoder) reads the question and a chunk together and gives a direct score for "does this answer that?". It is more accurate but slower, so it only examines the 10 candidates from the fast search and keeps the best 5.

Why:Accuracy. The author's notes in the code report the right chunk ranked first in 7 of 10 hard questions with search alone, and 10 of 10 with the reranker.Here:BAAI/bge-reranker-base. Set RERANKER_MODEL=none to skip it for speed.

3.6 Prompt: the written briefing prompts.py

The prompt is the exact text sent to the LLM. It is the "augmented" part of RAG. Here it contains (1) strict rules, (2) the last three question/answer pairs, so follow-ups like "what about page 5?" make sense, and (3) the five numbered sources plus your question. 

Sources:
<source id="1" file="handbook.pdf" page="12"> ...chunk text... </source>
<source id="2" file="handbook.pdf" page="13"> ...chunk text... </source>
Question: How many vacation days do I get?
Why:The rules make the model answer only from the sources, cite them as [1], and use one fixed "not found" sentence when nothing fits. Text inside <source> tags is declared to be data, never commands, which defends against a PDF that says "ignore your instructions".

4. Step-by-step technical architecture

Click any step, or just watch: the highlight moves through what happens when you ask a question. The table below it covers the full journey, including the upload.

1

Your question arrives. app.py collects it, the ticked documents, and recent chat history.

2

Question becomes numbers. embed_query() adds BGE's prefix and produces 384 numbers.

3

Fast search. ChromaDB returns the 10 nearest chunks. For follow-ups it also searches "previous question + this one".

4

Rerank. The cross-encoder scores each question+chunk pair and keeps the best 5.

5

Build the prompt. Rules + history + numbered sources + question are assembled.

6

The LLM writes. Ollama streams the answer word by word, and the app shows citations and source snippets.

Full journey: upload to answer

Code execution step What it does technically What it means in plain English
1. Upload
app.py: process_uploads		 Streamlit hands over the PDF as bytes. A key (name+size+id) prevents handling the same upload twice in a session. You drop a file in the sidebar; the app notes it as received.
2. Duplicate check
ingest_pdf		 Computes a SHA-256 hash of the bytes and asks ChromaDB if it exists. A fingerprint of the file. Same contents, even renamed, means it's already on the shelf.
3. Validate and read
load_pdf		 Checks extension, size (max 50 MB), %PDF- signature, corruption, password. PyMuPDF extracts text per page as paragraph blocks. Pages under 20 characters are skipped. The librarian checks the book is real, undamaged and unlocked, then copies out the text. Scanned images of text can't be read.
4. Chunk
chunk_document		 Splits each page into pieces up to 1000 characters with 150-character overlap, tagged with file, page and index. Pages become labeled index cards.
5. Embed chunks
embed_documents		 The BGE model converts chunks into 384-number vectors, 32 at a time, on the CPU. Every card gets a meaning fingerprint.
6. Store
add_chunks		 Upserts vector, text and metadata into ChromaDB using IDs built from the file hash. Cards are filed. Filing the same card twice replaces it, and it survives restarts.
7. Ask
answer()		 Gathers selected documents and history, calls answer_question. You type a question and pick where to look.
8. Embed question
embed_query		 Prefix + question becomes a vector. The question gets its own fingerprint.
9. Vector search
store.search		 Top 10 by cosine similarity, optionally filtered to ticked PDFs. Grab the 10 cards closest in meaning.
10. Rerank
reranker.rerank		 Cross-encoder keeps the best 5. The bare question's top match is guaranteed a slot so a topic change isn't lost. A careful second reader re-sorts the pile.
11. Build prompt
build_messages		 System rules, last 3 Q&A pairs, numbered sources, question. A briefing note for the writer.
12. Generate
stream_chat		 Sends it to local Ollama (temperature 0.1, 8192-token window) and streams tokens back. The writer composes; you watch it appear.
13. Display
app.py		 Streams text, finds [n] citations, shows a Sources panel with file, page, relevance and a snippet. You get an answer with checkable footnotes.

6. A worked example

This is an illustration (the numbers are made up) of one question travelling through the system. Suppose you uploaded handbook.pdf.

Indexing

Page 12 says: "Full-time staff receive 24 days of paid annual leave per year." The chunker keeps it as a chunk labeled handbook.pdf, page 12, chunk 0. The embedder turns it into 384 numbers. ChromaDB stores text, numbers and label.

Asking

You type: "How many vacation days do I get?" No word matches "annual leave", but the meaning-numbers are close, so the page-12 chunk lands in the top 10.

Reranking

Another chunk about "working days in a month" shares the word "days" and ranks high in search. The reranker sees it doesn't answer the question and moves page 12 to first place.

Generating

The LLM reads the five sources and replies: "Full-time staff receive 24 days of paid annual leave per year [1]." The Sources panel shows handbook.pdf, page 12 and marks [1] as cited.

The key insight of RAG: the LLM never "knew" your policy. It was handed the right paragraph at the right moment. Quality depends mostly on retrieval. If the right chunk isn't found, even a great LLM can't answer correctly, which is why this project invests in chunking, the BGE prefix and a reranker.
Follow-up questions: if you then ask "and for part-time staff?", that question alone is vague. retrieve() also searches with the previous question prepended, keeps each chunk's best score, and reranks against the combined query. This is how the bot resolves words like "it" and "that".

7. File and code reference

Libraries actually used: this project does not use LangChain or PyPDF. It uses PyMuPDF (PDFs), sentence-transformers + PyTorch (embedding and reranking models), ChromaDB (database), Ollama (LLM) and Streamlit (web page). Chunking, retrieval logic and prompts are hand-written.
Library Job Why it's here
Streamlit Builds the web page from Python Chat box, sidebar, upload button with no HTML or JavaScript.
PyMuPDF Extracts text with page numbers Fast, and reads from in-memory bytes like uploads.
sentence-transformers, torch Run the embedding and reranker models Meaning-numbers and relevance scores on a normal CPU.
ChromaDB Stores and searches vectors Server-free, saves to disk.
ollama, httpx Talk to the local LLM Send prompts, receive streamed text, catch timeouts.
python-dotenv Reads optional .env Change settings without editing code.

app.py interface

What: the Streamlit page. Why it's careful: Streamlit re-runs the whole script on every click, so the heavy pipeline is created once with @st.cache_resource, and chat history is kept in st.session_state. It contains no AI logic. 

@st.cache_resource
def get_pipeline():
    return RAGPipeline(load_settings())

config.py settings

What: one Settings object with every number (chunk size 1000, overlap 150, top_k 5, models). How: defaults, then .env, then real environment variables. Invalid values raise a clear ConfigError.

pdf_loader.py reading

What: validates and reads the PDF. Why blocks: PDFs store positioned lines, not sentences, so it reads paragraph blocks, joins their lines and repairs hyphenated words. 

page.get_text("blocks", sort=True)

chunker.py cutting

How: _split breaks text at paragraph, then sentence, then word boundaries. _merge packs pieces up to the size limit and starts each new chunk with an overlap tail from the previous one.

embeddings.py numbers

What: Embedder with embed_documents (no prefix) and embed_query (with prefix). It loads the model from local files first and caches it, because loading takes seconds.

vector_store.py database

How: PersistentClient saves to disk; upsert with hash-based IDs avoids duplicates; a where filter limits search to ticked PDFs; score = 1 − cosine distance. 

collection.query(
  query_embeddings=[vec], n_results=10)

reranker.py re-sorting

How: builds (question, chunk) pairs, calls the cross-encoder's predict, sorts by score, returns the best top_k.

prompts.py instructions

What: the system rules, the fixed "not found" sentence, and the functions that number the sources and trim history to the last 3 turns.

llm.py writer

How: stream_chat uses stream=True so text appears gradually (CPU answers can take 10-30 s). think=False asks for the answer without the model's reasoning. check_ready() turns "Ollama not running" into a friendly message.

rag_pipeline.py conductor

What: RAGPipeline ties it all together. ingest_pdf() = hash, load, chunk, store (cleaning up if storing fails). answer_question() = retrieve, build prompt, stream. Parts can be swapped for fakes in tests.

models.py, exceptions.py shared

Small immutable records (Chunk, RetrievedChunk, Answer) carry file and page through every step, which makes citations possible. Each error type holds a plain-English user_message.

scripts/ and tests/ tools

verify_setup.py checks your install. chat_cli.py chats in the terminal. inspect_pdf.py shows extracted text and chunks. search_pdf.py shows raw search hits. tests/ is a pytest suite using in-memory PDFs.

8. Run, test, and troubleshoot

No API keys required. The project was verified on Python 3.12 and Windows 11 (CPU only). Commands are PowerShell; macOS/Linux alternatives are noted.
  1. Install Python 3.12 (the project requires 3.12.x). Check: python --version
  2. Get the code. 
    git clone https://github.com/KrishnaPankhania06/chatbot-task.git
cd "chatbot-task/pdf chatbot"
  3. Create a virtual environment (an isolated box for this project's packages). 
    python -m venv .venv
.\.venv\Scripts\Activate.ps1      # macOS/Linux: source .venv/bin/activate
  4. Install dependencies. This is a large download because of PyTorch. 
    python -m pip install -r requirements.txt
  5. Install Ollama from ollama.com, start it, then download the language model: 
    ollama pull qwen3:4b-instruct
  6. (Optional) environment variables. Create a file named .env next to app.py. Every value has a default, so skip this unless you want changes. The code mentions a .env.example, but the repository doesn't contain one. 
    LLM_MODEL=qwen3:4b-instruct
TOP_K=5
CHUNK_SIZE=1000
RERANKER_MODEL=none        # faster, slightly less accurate
OLLAMA_HOST=http://localhost:11434
  7. (Recommended) verify the setup. Internet is needed once, because the embedding and reranker models download from Hugging Face on first use. 
    python scripts/verify_setup.py
  8. Start the app. 
    streamlit run app.py
    It opens at http://localhost:8501. The first start can take a minute or two.
  9. Use it. Upload PDFs in the sidebar, wait for the "chunks from pages" message, tick the documents to search, and ask. Open Sources under an answer to check the pages.
  10. (Optional) run the tests. 
    python -m pytest -m "not model and not ollama"
